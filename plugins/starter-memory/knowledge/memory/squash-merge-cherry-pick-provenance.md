When you cherry-pick a change from another in-flight PR and both PRs later land independently, the receiving PR goes `DIRTY` at the moment the source PR squash-merges to main. The cherry-picked file is the primary conflict surface: main now carries the squash-merge version; HEAD carries the cherry-pick plus any enhancements layered on top.

**Resolution:** `git checkout --ours` on the conflicted file is usually correct when HEAD has further changes layered on top of the cherry-pick (the cherry-pick was a stepping stone, not the final state). If HEAD is identical to the cherry-pick with no enhancements, inspect both versions before deciding.

**Commit message trap:** the commit that resolves the conflict must use a valid conventional-commit type. `merge:` is NOT an allowed type (the commit-msg-format hook rejects it). Use `chore:` instead, or use the git-default `Merge branch 'main' into ...` autogenerated subject which most hooks pass through.

**Why:** A squash-merge rewrites the source PR's commits as a single new commit on main. If the receiving PR has that same change (via cherry-pick), Git sees two divergent histories for the same file and marks the PR DIRTY.

**How to apply:**
- When cherry-picking from an in-flight PR, plan for a DIRTY-resolution step before the source PR merges. The right resolution is usually `--ours` on the conflicted file.
- After pushing the merge commit, GitHub's `mergeStateStatus` takes a few seconds to recompute. Poll with `until [ "$(gh pr view N --json mergeStateStatus --jq '.mergeStateStatus')" != "DIRTY" ]; do sleep 5; done` rather than assuming the push immediately clears DIRTY.
- Use `chore:` (not `merge:`) for merge-resolution commits when a conventional-commit hook is active.
